文档切片
```
我的思路可以概括成一句话：结构优先、语义兜底、长度控制、重叠保护。

  第一步，先按文档结构切。 我不会上来就按固定长度硬切，那样容易把语义切碎。比如 Markdown
  文档按标题层级拆章节，表格整个保留单独成块，代码按函数边界切。这一步的目的是让每个 chunk 尽量是一个完整的语义单元。

  第二步，结构内超长的块再做二次切分。
  用递归字符切分的方式，按段落、句号、换行这个优先级逐级往下拆，直到控制在目标长度内，一般 512 token
  左右——这个值不是拍脑袋定的，主要考虑 Embedding 模型比如 BGE 在 512 长度上表征效果最好。

  第三步，块与块之间保留 10% 到 15% 的重叠。 这是踩过坑总结出来的：如果答案刚好落在两个 chunk
  的边界上，没有重叠就必然召回失败。

  还有两个工程细节我觉得很关键：

  一是切完的 chunk 前面会拼接标题路径，比如"产品手册 > 第三章 >
  安装配置"，这样检索和生成时上下文感会强很多，相当于给每个碎片加上了"它从哪来"的路标。

  二是特殊内容特殊处理：表格不切散，整表转 Markdown 入库，配一段文字描述做索引；图片用多模态模型生成描述文本再向量化。

  最后，切片策略一定要进评估闭环。 我会准备一批标注好的"问题对应答案段落"，测 Top-K 召回命中率；Bad Case 重点排查是不是
  答案被切断了——这是最常见的失败原因。实际项目里，从固定长度切分优化到这套组合策略后，召回命中率提升了十几个点。

  所以总结下来：切片不是预处理的小步骤，它直接决定了 RAG
  效果的上限——切得好，后面的检索和生成都顺；切得烂，再强的模型也救不回来。
```

模型幻觉
```
关于模型幻觉，我的方法论是三道防线：不给它编的机会、编了能拦住、拦不住能发现。

先说根因。幻觉本质上有两类：事实性幻觉是模型编造不存在的事实，忠实性幻觉是给了材料但答非所料。根源在于模型的知识有边
界，而概率生成的本质决定了它优先'说得通顺'而不是'说得正确'。

第一道防线在输入侧，核心就是 RAG——让模型基于检索到的真实文档回答，而不是靠记忆自由发挥。但有个关键点：检索不到就要敢
于拒答，设相似度阈值，宁可说不知道，也不硬答。检索错了比不检索更可怕。

第二道防线在生成侧，靠 Prompt 约束。我实战里最有效的是三招：一是强制引用，要求每个事实标注来源片段编号，模型一旦要交
代出处就不敢乱编；二是明确拒答指令，资料里没有就说不；三是 Few-shot
给拒答示范，比单纯下指令管用得多。参数上温度调低到 0 到 0.3，事实类任务不给创作自由。

第三道防线在输出侧，做校验兜底。生成完让模型回查——答案里每个论断是否都能在检索文档中找到依据，找不到的就重写。数字、
日期这类硬信息用正则提取后和原文比对。我在实际项目里还跑通过完整的数据闭环：幻觉 Bad Case
回流到标注平台，分析是检索错了、Prompt 没约束住还是模型能力问题，针对性迭代。

最后一点，幻觉治理必须有量化评估，否则就是玄学。我会构建带标准答案的事实性测试集，用忠实度指标衡量答案和检索文档的一
致性，同时监控拒答率——拒答率异常升高说明检索链路有问题，过低说明模型在硬答。

总结一句：幻觉无法根除，但可以通过'RAG 补知识、Prompt
强约束、输出做校验、闭环持续迭代'把它控制在业务可接受的范围内。谢谢。
```

 一、Agent 与 RAG 类（必问区）

  Q1：讲一遍你做过的 RAG 全链路

我以企业知识库场景讲一遍完整链路。离线侧分四步：第一步文档解析与切片，结构优先——Markdown
按标题层级、表格整表保留，超长块再递归切分到 512 token 左右，块间留 10%~15% 重叠，每个 chunk 拼接标题路径；第二步
Embedding 入库，中文场景我选 BGE-M3，同时生成稠密向量进 FAISS、分词进 BM25 索引；在线侧：用户 Query
进来先做改写和意图识别，然后多路召回——向量检索取语义相关、BM25 兜关键词精确匹配，两路结果合并后过 Rerank
模型精排，取 Top 3~5 拼进
Prompt；生成时强制引用来源，检索不到就拒答，最后输出侧做回查校验。整个链路由数据闭环驱动迭代：Bad Case
回流标注，分析是切片、检索还是生成的问题，针对性优化。这条链路我在百度意图分类和合规比对项目里都完整跑通过，每个环节
都有量化评估——召回测 Recall@K，生成测忠实度和准确率。

  Q2：LangChain 的 Agent 是怎么工作的？

LangChain Agent 的核心是 ReAct 模式——推理（Reason）和行动（Act）交替循环。具体流程：用户问题进来后，LLM
先推理「我需要做什么」，决定调用哪个 Tool、传什么参数；框架执行 Tool 拿到观察结果（Observation），再喂回给 LLM
继续推理，直到模型判断信息足够、输出最终答案。工程实现上有几个关键点：一是 Tool 的描述写得好不好直接决定 Agent
选工具准不准，名称、功能说明、参数 Schema 都要清晰；二是要设最大迭代次数，防止 Agent 死循环烧 token；三是 Memory
模块管多轮对话历史，简单的用 ConversationBufferMemory，长对话用 SummaryMemory
压缩。我实际开发中还会加一层意图路由——先判断用户意图类型，走固定 Chain 的就不启动 Agent 循环，因为 Agent
模式灵活但慢且不可控，能确定的流程用 Chain，真正需要动态决策的才用 Agent，这是成本和效果的平衡。

  Q3：MCP 协议是什么？怎么用？

MCP（Model Context Protocol）是 Anthropic 提出的模型与外部工具/数据源之间的标准化协议，可以理解为「AI 应用的 USB-C
接口」。它解决的核心问题是：以前每接一个工具都要写一套自定义集成代码，N 个模型 × M 个工具就是 N×M 的集成量；MCP
把工具封装成统一的 Server，客户端按标准协议调用，变成 N+M。架构上分三层：MCP Host（如 Claude Desktop、IDE）、MCP
Client（维持与 Server 的连接）、MCP Server（暴露三类能力——Tools 可执行函数、Resources 数据资源、Prompts
模板）。传输层支持 stdio（本地进程）和 SSE/HTTP（远程服务）。实际使用中，比如我要让 Agent 查数据库，不需要改 Agent
代码，只需要起一个数据库 MCP Server，在配置里注册，Agent 就能自动发现和调用它的工具。对我来说 MCP 最大的价值是让
Tool 开发生态标准化了，我在 LangChain 里开发的自定义 Tool，改造一下就能以 MCP Server 形式复用给其他 Agent 框架。

  Q4：你的 123 类意图体系是怎么设计的？

这套体系的核心设计原则是以用户意图动作为中心，而不是以行业内容为中心。传统行业分类回答的是「用户在问什么领域」，而
AI 交互场景要回答的是「用户想让 AI
干什么」——同样一句「帮我写一篇关于猫的文章」，行业分类是宠物，但意图是内容生成。我自上而下设计了 6
大一级意图：信息查询、内容生成、任务处理、咨询决策、操作执行、互动体验，然后结合真实 Query
日志聚类分析，自下而上验证和细分成 123 个叶子类。医疗垂类单独设计了 23
个细粒度意图，按判断型、决策型、指导型、了解型区分，因为医疗 Query
风险高，不同意图要路由到完全不同的应答策略。这套体系的价值在于直接驱动 Agent
路由：内容生成意图走生成链路，任务处理意图调 Tool，信息查询走 RAG 检索——意图标签就是 Agent
决策层的输入信号。落地时通过缓存召回 + ERNIE 推理 + 规则引擎覆盖的多级架构保证准确率，配合 LabelCheck
门控保证标签合法性。

  Q5：Rerank 重排怎么做？为什么需要它？

需要 Rerank 的根本原因是向量检索的双塔结构交互不充分——Query
和文档分别独立编码成向量，靠余弦相似度打分，细粒度的语义交互信息丢了。而 Rerank 模型（比如
bge-reranker）是交叉编码结构，把 Query 和文档拼在一起进模型，逐对算相关性分数，精度高得多。但它慢——没法对全库百万文
档逐对打分，所以工程上是两段式：检索管召回（快、粗）、Rerank 管精排（慢、准），Rerank 只对召回的 Top 50~100
重新打分，取最终 Top 3~5。实际收益很明显，通常能把最终答案的相关性提升 10 个点以上。另外多路召回场景 Rerank
还承担统一打分的作用——向量分数和 BM25 分数量纲不同没法直接比，合并后交给 Rerank 统一重排就解决了。选型上中文场景
bge-reranker-v2 是主流，对延迟敏感的场景可以用小一号的 base 版本。

  Q6：Agent 的 Memory 怎么实现？

分短期和长期两层。短期记忆就是会话上下文，最简单的是把完整对话历史塞进 Prompt，但 token
会爆，所以工程上有几种策略：窗口记忆只保留最近 K 轮；摘要记忆让模型滚动总结历史压缩
token；实体记忆提取对话中的人物、偏好等关键事实单独存。长期记忆跨会话持久化，一般存向量数据库——把用户偏好、历史结论
Embedding 入库，新会话先检索相关记忆再生成。我在项目里的实践是分层组合：当前会话用窗口 + 摘要混合策略控制 token
成本，用户画像和长期偏好走向量库检索召回。关键的设计考量是记忆不是越多越好——塞太多无关历史会稀释模型注意力、引入噪声
，所以记忆写入时要做重要性筛选，召回时也要设相关性阈值，这和 RAG 检索是同一套逻辑。

  二、大模型工程化类

  Q7：Spark 集群上怎么做大模型批量推理？

核心思路是把大模型推理当成一个分布式 UDF 任务跑。具体做法：数据侧，Query 日志 ETL 后按分区读入 Spark
DataFrame；推理侧，每个 Executor 上加载模型推理环境——ERNIE 这类内部模型通过 Paddle 推理服务化接口调用，GPT/通义这类
API 模型则封装成带鉴权和重试的 HTTP 调用函数，通过 mapPartitions
让每个分区内复用连接和批量请求，避免逐条调用的开销。三个关键工程问题：一是限流，API 模型有 QPS 上限，我用 Redis
令牌桶做全局限流，所有 Executor 共享配额；二是容错，推理失败的记录单独落盘，重试机制 + 最终兜底标签，保证小时级任务
SLA；三是成本，能上缓存的先走缓存——我用双缓存机制，命中缓存的 Query 不走模型推理，百万级 Query
里缓存命中率很高，大幅省推理资源。这套架构支撑了每天百万级 Query 的分类任务稳定运行。

  Q8：Prompt 工程你有哪些实战经验？

我的方法论是指令明确化、示例场景化、输出结构化。以通义大模型违规比对项目为例：任务是让模型比对化妆品网备信息和商品公
示信息是否一致。第一版 Prompt 只描述了任务，准确率不到 80%；优化后我做了四件事：一是角色和任务边界写死——'你是合规审
核员，只判断给定两文本的一致性，不做额外推测'；二是Few-shot 给典型判例，特别是边界
Case——比如规格写法不同但实际一致的该判合规；三是判定标准逐条列出，把'冒用备案号、维度不一致'这些违规类型定义成明确
checklist；四是输出格式用正则约束——要求固定格式返回判定结果和理由，我再写正则解析成结构化数据落库。四步优化后准确率
提升到 95% 以上。另外的经验是 CoT 思维链适合推理类任务，但分类比对类任务重点是判定标准明确；所有 Prompt
迭代都要有评测集兜底，不然就是凭感觉调参。

  Q9：Ollama 本地部署和量化了解多少？

Ollama 的价值是把开源模型本地部署的成本降到一条命令，适合数据敏感场景和低成本验证。我用它部署过 GLM、Llama
系列。部署上的关键点：一是显存估算，7B 模型 FP16 需要约 14GB 显存，Q4 量化后 4GB
左右就能跑，消费级显卡可行；二是量化权衡，量化本质是把权重从 FP16 压到 INT8/INT4，Q8 几乎无损，Q4
损失可接受但长文本推理能力会下降，Q2 以下基本不可用——我的原则是能 Q8 不
Q4，生成质量敏感的环节量化要慎重；三是并发能力有限，Ollama 适合开发和中小流量场景，高并发生产环境要用 vLLM
这类支持连续批处理的推理框架。实际项目里我用 Ollama 做本地原型验证和离线标注辅助，验证链路和 Prompt
可行性后，生产环境再切到集群推理或 API。

  三、项目深挖类（面试官会照着简历抠）

  Q10：双缓存 + XGBoost 复现概率是怎么回事？

背景是百度搜索 Query 分类系统每小时处理百万级 Query，全部走模型推理成本扛不住，而 Query 分布高度长尾——头部 Query
反复出现。所以设计了缓存机制：命中的直接返回历史标签。问题是缓存字典容量上限 1 亿条，哪些该留、哪些该淘汰？这就是
XGBoost 解决的问题：用历史行为特征（Query 历史 PV、出现的时间间隔分布、长度、类目等）训练模型，预测每条 Query
未来一段时间内的复现概率，复现概率低的淘汰出缓存，把容量留给高价值
Query。双缓存是指短周期缓存（小时级，响应突发热点，比如热搜事件 Query 突然爆发）和长周期缓存（天级，沉淀稳定高频
Query），两套配合兼顾突发性和稳定性。效果是大幅减少重复模型推理，同时通过文件锁和异常自动回退机制保证缓存读写不影响
小时级任务 SLA。

  Q11：9 路信号融合具体怎么做的？

背景是单一路径的标签都不够可靠：专家词表准但覆盖低，模型覆盖高但有误差，规则快但生硬。所以融合了 9
路信号：传统专家词典、AI 专家词表、意图专家词表、电商模型、缓存模型标签、ERNIE Query 级模型、ERNIE PV
级模型、规则引擎、热榜信号。融合策略核心有两点：一是优先级分层，专家词表是人工精修的，置信度最高优先采用；模型和规则
按历史准确率排优先级；二是 isPosterior 标志做 Query 级和 PV 级自适应切换——Query 级标签只看这条 Query 本身，PV
级标签聚合了这个 Query 下所有搜索行为信号，当 Query 级置信度不足时切换到 PV
级标签兜底。多信号融合本质上是用冗余换稳定性——任何单路信号波动都不会直接影响最终输出，这也是系统能扛住小时级生产 SLA
的关键设计。

  Q12：LabelCheck 质量门控怎么做的？

LabelCheck 解决的是分类结果写入数仓前的最后一道质量关。背景是标签来自多个来源——模型、规则、缓存、专家词表，任何一路
出问题都可能产生非法标签：比如标签码表里不存在的值、层级关系错误（三级标签挂错一级类目）、空值。LabelCheck
的机制是：全量输出在写入前与标签码表自动比对，非法标签阻断写入并告警，绝不让脏数据进数仓污染下游。配合它的是
label_source 溯源机制——每条记录都携带来源标记，cachedModelLabel、modelLabel、ruleLabel、expert、aiExpert、hotNews
六种，这样下游可以按来源统计精度，出了问题能快速定位是哪条链路引入的。这套「门控 +
溯源」组合的价值在于让质量可度量、问题可归因，也是 Bad Case 数据闭环的基础设施——没有来源标记，迭代就无从下手。

  Q13：在线打标 Web 平台是你独立开发的？讲技术细节

是的，前后端独立交付。背景是意图分类体系从 0 建设，训练样本和评测样本都缺，需要让 PM
和业务人员能低门槛参与标注。功能设计上：Query 按业务线和场景抽样推送，标注界面展示 Query
原文和当前意图体系树，支持搜索定位标签、多标签标注、疑难 Case 标记跳过；标注结果入库时记录标注人、时间、标签路径。工
程上的关键设计：一是预填模型预测标签，标注员只需要确认或修改，效率比从零标提升好几倍；二是质量互验机制，同一批 Query
分发给多人，计算标注一致性，一致性低的进仲裁流程；三是样本直接对接迭代链路——标注完成的样本自动进入训练集和评测集，
支撑模型迭代和 LabelCheck 码表更新。这个平台打通了「线上 Bad Case → 人工标注 →
策略/模型迭代」的完整闭环，让分类体系的准确率能够持续爬坡。

  Q14：小时级任务出故障你怎么处理？

我在百度参与线上值班，处理过分类波动、任务失败、数据延迟、标签异常几类问题，方法论是先止血、再定位、后复盘。止血层面
有预案：任务失败有自动重试，重试不行有历史缓存自动回退机制——用上一周期数据兜底，保证下游就绪时间
SLA；分类结果波动超过阈值触发告警，先判断是否影响下游决定是否拦截发布。定位层面按链路逐段排查：数据源延迟查上游
ETL，推理失败查集群资源和限流日志，标签异常查 LabelCheck 拦截记录和 label_source 分布变化——label_source
分布突变往往是定位入口，比如某来源占比突然飙升，基本就是那路出问题。复盘层面每个故障形成记录，能加监控的加监控，能自
动化的人工动作自动化。这套体系让我值班期间多次在 SLA 前消化故障，也推动了不少稳定性改造落地。

  四、机器学习与数据底座类（中概率）

  Q15：XGBoost 原理和样本不均衡怎么处理？

XGBoost
是梯度提升树的高效工程实现，核心思想是串行训练多棵决策树，每棵拟合前面模型的残差（负梯度），最终加权求和。相比原始
GBDT，它的改进：目标函数里加了正则项控制树的复杂度防过拟合；用二阶泰勒展开利用一阶和二阶梯度信息，收敛更快；工程上支
持列抽样、并行化、缺失值自动处理。样本不均衡我有几种实战手段：一是 scale_pos_weight
参数调整正负样本权重；二是采样层面——多数类欠采样或 SMOTE
过采样，但我更倾向保留原始分布调权重，采样容易引入偏差；三是评估指标换赛道——不均衡数据下准确率没意义，看 AUC、PR
曲线、F1 和召回率；四是阈值调优，按业务对精确率/召回率的偏好调分类阈值，而不是默认 0.5。Query
复现预测项目里正负样本就是天然不均衡的，主要靠权重 + 阈值调优解决。

  Q16：Spark 数据倾斜怎么处理？

数据倾斜的本质是某个 Key 的数据量远超其他 Key，导致单个 Task 拖垮整个 Stage。我处理过的手段按优先级：第一，定位——看
Spark UI 哪个 Stage 的 Task 耗时中位数和最大值差距悬殊，确认倾斜 Key；第二，加盐打散——给热点 Key
加随机前缀，把一个超大分组拆成 N 个，局部聚合后再去盐全局聚合，两阶段聚合是最常用的解法；第三，Map 端 Join——大表
Join 小表时把小表广播出去（Broadcast Join），直接在 Map 端完成关联，从根上避免 Shuffle
倾斜；第四，过滤或单独处理热点 Key——比如空值 Key 提前过滤，头部 Key 拆出来单独算再
Union。另外资源参数层面，合理设置并行度和 Executor 内存也能缓解，但治标不治本——治本还是要从 Key 的分布下手。

  Q17：Flink 水位线和状态管理讲讲？

水位线解决的是乱序事件的时间语义问题：实时数据到达有延迟和乱序，窗口什么时候关闭不能只看窗口结束时间，水位线就是系统
认为'该时间之前的数据基本到齐了'的时间戳——水位线 = 观察到的最大事件时间 -
允许的最大乱序延迟。窗口触发条件是水位线越过窗口结束时间，迟到数据可以通过 allowedLateness
宽限或侧输出流兜底。状态管理方面，Flink 的算子状态存后端（内存/RocksDB），大状态用 RocksDB 增量
Checkpoint；Checkpoint 机制做故障恢复——定期快照状态，失败时从最近一次 Checkpoint 恢复，配合两阶段提交的 Sink
可以实现端到端精确一次语义。电商直播大屏项目里，实时指标计算就是靠水位线处理 DataHub 数据的乱序，Checkpoint
保证任务重启后指标不丢不重。

  Q18：你为什么从数据开发转 Agent 开发？你的优势是什么？

其实这不是转型，是能力栈的自然延伸。我的路径是：数据开发打底——数仓、实时计算、数据质量，让我对'数据怎么流动、质量怎
么保障'有工程直觉；然后在商务部项目中第一次把通义大模型嵌进监管流水线做违规比对，发现大模型落地的核心瓶颈不在模型本
身，而在数据链路和工程化；再到百度做意图分类，站在 Agent
体系里理解了数据、标签、路由决策的关系。所以我的差异化优势是三点：一是既懂 Agent 上层应用又懂底层数据底座，很多
Agent 项目死在数据质量和评估闭环上，而这正是我的主场；二是大规模工程化能力，Spark 集群批量推理、百万级小时级任务的稳
定性保障，这个经验纯应用层开发者很少具备；三是全栈交付能力，从意图体系设计、模型推理链路，到打标 Web 平台、API
接口，我能一个人把闭环跑通。Agent 工程师未来拼的是体系化落地能力，这正好是我的能力拼图。

  Q19：你未来的职业规划是什么？

短期一到两年，我希望在 Agent 开发方向做深——从现在的意图路由、RAG 检索层，往更上层的复杂任务规划、多 Agent
协作方向拓展，把 LangChain 和 MCP 的工程经验沉淀成能支撑生产级 Agent 产品的完整方法论。中期来看，我观察到 Agent
的竞争力正在从'调通链路'转向'数据闭环和持续进化能力'——谁能建立高质量的评估体系、让 Agent 从 Bad Case 中自动学习，谁
的产品就能持续拉开差距。我在百度做的标注闭环、质量门控、溯源体系就是这个方向的实践，未来希望把这套能力应用到更完整的
Agent 产品上。长期我希望成为既懂算法体系又懂工程落地的 Agent 技术负责人，带团队做有真实业务价值的 AI
产品。贵司这个岗位的业务方向和我的规划很匹配，这也是我投递的原因。
