# 17 种 RAG 方案整理

> 检索增强生成（Retrieval-Augmented Generation）不是一套固定流水线，而是可按场景组合的技术模块。  
> 本文按三类整理 17 种常见方案：文档分块、检索排序、反馈与自适应，并附选型建议。

---

## 核心判断

传统大模型有两个硬伤：**知识过时**、**容易幻觉**。RAG 的做法是：先从外部知识库检索，再把检索结果塞进提示词，让模型「开卷答题」。

- RAG 可以按 **文档怎么切、检索怎么排、系统怎么自适应** 拆开优化
- 17 种方案是模块，不是必须一次全上
- **先跑通最简 RAG，再针对真实痛点加模块**，不要一上来上 GraphRAG + Multi-Agent 全家桶

没有全场最佳 RAG，只有最适合当前数据、延迟和预算的组合。

---

## 一、文档分块：知识表示质量（1–5）

检索上限往往卡在切块，不在模型。块太小会切断语义，块太大会混进多个主题。

### 1. Simple RAG（基础 RAG）

**在做什么**

文档切块 → 向量化 → TopK 检索 → 拼进提示词生成。这是 RAG 的毛坯房，也是所有进阶方案的基线。

**解决什么**

最快验证「检索 + 生成」这条链路能不能跑通。

**痛点**

固定长度切块容易把一句话、一个论点切断；召回和精度都一般，只适合 Demo、短文档、功能验证。

**适用场景**

- 快速 POC
- 小型 FAQ
- 作为后续优化的对照基线

---

### 2. Semantic Chunking（语义分块）

**在做什么**

不按字数切。先把文档拆成句子，计算相邻句的向量相似度；相似度骤降说明换话题了，就在这里切开。

**解决什么**

保证每个块内部主题完整，避免「半截子句子」进索引。

**代价**

比固定长度切块更耗计算，需要调相似度阈值和最小 / 最大块长。

**适用场景**

- 长文、主题会切换的材料
- 对召回质量要求高于「先能跑」

---

### 3. Context Enriched（上下文增强检索）

**在做什么**

检索命中一个块时，把前后邻居段落一起带给模型，相当于「块 + 窗口上下文」。

**解决什么**

长文档推理更连贯，避免只搜到半段、模型看不懂指代。

**代价**

上下文变长，token 成本和延迟上升；窗口过大也会引入噪声。

**适用场景**

- 手册、论文、制度文件
- 答案依赖前后文才能读懂的文档

---

### 4. Contextual Headers（块头标签）

**在做什么**

提取章节名、标题路径等结构性标签，和正文一起向量化（或作为元数据过滤）。

**解决什么**

块离开原文后会丢失「它属于哪一章」。标题能给检索和生成提供定位信息。

**适用场景**

- 技术手册、法律文书、产品文档
- 多份文档术语高度重叠、必须靠章节区分

---

### 5. Document Augmentation（文档增强）

**在做什么**

给同一文档做多视图索引：摘要、正文、元数据，甚至给每个块生成「可能被问到的问题」，再用这些问题去检索，命中后再回到原文。

**解决什么**

短问题也能对上长段落；查询和文档语体不一致时，召回更好。

**代价**

索引体积和预处理成本增加；生成的问题质量会影响检索。

**适用场景**

- 用户提问很短、很口语
- 文档很长、直接用正文向量对不上问题

---

## 二、检索排序：命中精度（6–9）

搜得到，不等于搜得准。这一段在召回和精度之间做平衡。

### 6. Query Transformation（查询改写）

**在做什么**

用大模型把用户问题改写成多个同义问法、子问题或更规范的检索式，再分别检索、合并去重。常见实现：MultiQueryRetriever、问题分解、Step-Back。

**解决什么**

口语、问法飘、同义词对不上原文。

**代价**

多次检索，延迟和费用上升；改写不好会引入无关文档。

**适用场景**

- 客服、个人助手
- 用户提问风格多变

---

### 7. Reranker（重排序）

**在做什么**

先用向量 / 关键词做宽召回（比如 Top 50），再用 Cross-Encoder 对「问题 + 文档」二次打分，只把最相关的几段交给生成模型。

**解决什么**

双塔检索快但不精；精排能明显抬精度，是生产环境最常用的加分项之一。

**代价**

多一次模型调用；TopN 太大时延迟明显。

**适用场景**

- 生产环境、对准确率有要求
- 已经能召回到相关内容，但排序不好

---

### 8. RSE（Relevant Segment Extraction，相关片段提取）

**在做什么**

检索到较长段落后，再在段内定位真正有用的句子或连续片段，而不是整段塞进提示词。

**解决什么**

减少噪声，保留关键证据，避免模型被无关句子带偏。

**适用场景**

- 块比较大、一段里只有几句有用
- 需要引用原文关键句的场景

---

### 9. Contextual Compression（上下文压缩）

**在做什么**

生成前按问题过滤、压缩检索结果，只留相关句子。常见组件：LangChain ContextCompressor、各类压缩模型。

**解决什么**

省 token、降延迟、少被噪声带偏。

**代价**

压缩过度会丢掉桥接信息；多一次过滤调用。

**适用场景**

- 上下文窗口紧、成本敏感
- 召回结果又长又杂

## 三、反馈与自适应：系统怎么进化（10–17）

前面解决「这一次答得好不好」，这一类解决「要不要检索、检索差了怎么办、下次会不会更好」。

### 10. Feedback Loop（反馈闭环）

**在做什么**

收集用户点击、点赞、点踩、人工纠正，用来重训或调整排序、改写、切块策略。

**解决什么**

让系统跟着真实使用数据进化，而不是一次性调参。

**适用场景**

- 智能客服、站内搜索
- 有稳定流量和标注 / 行为日志

---

### 11. Adaptive RAG（自适应路由）

**在做什么**

先判断问题类型，再走不同路径：不检索 / 单跳检索 / 多跳检索。简单问候不该搜知识库，复杂对比不该只搜一次。

**解决什么**

查询复杂度差异大时，用同一条流水线要么浪费、要么不够用。

**适用场景**

- 生产里既有闲聊、又有事实问答、又有多步推理
- 要同时管效果和成本

---

### 12. Self RAG（自我决策 RAG）

**在做什么**

模型在流程中自我审视：这个问题需要检索吗？检索到的文档相关吗？答案有没有超出资料瞎编？

**解决什么**

减少无效检索，也减少「资料对了但回答夹带私货」。

**代价**

实现和延迟更高，通常要反思 token 或多轮判断。

**适用场景**

- 对幻觉零容忍的垂直领域
- 有些问题其实不需要外挂知识

---

### 13. Knowledge Graph / GraphRAG（知识图谱 RAG）

**在做什么**

从文档抽取实体和关系，建成图谱；检索时找实体、路径或子图，而不是只找文本块。也可做社区摘要，回答全局性问题。

**解决什么**

跨文档多跳推理、人物关系、制度沿革、组织架构。纯向量检索很难把「A 的上级的上级」这种问题串起来。

**代价**

构建和维护成本高，抽取质量决定上限。

**适用场景**

- 需要多跳、结构化关系
- 对可解释性、溯源要求高

---

### 14. Hierarchical Indices（多级索引）

**在做什么**

建文档树：上层是章节 / 摘要，下层是细节块。先检索粗粒度，再下钻到细粒度（也可父子文档：子块检索、父块生成）。

**解决什么**

长文档里既有「这篇在讲什么」也有「某一条具体规定是什么」。

**适用场景**

- 书籍、年报、长篇制度
- 查询粒度忽大忽小

---

### 15. HyDE（Hypothetical Document Embeddings，假设文档嵌入）

**在做什么**

先让模型写一个「假想答案」（不必完全正确），用假想答案的向量去检索真实文档。检索到的原文才是证据，假想答案只当检索桥梁。

**解决什么**

用户问题太短、和文档语体差太远，短问句和长技术段在向量空间对不上。

**代价**

多一次生成；假想答案跑偏会带偏检索。

**适用场景**

- 短问题、抽象问题
- 术语密集、问法与行文差异大

---

### 16. Fusion（融合检索 / RAG Fusion）

**在做什么**

多路检索再融合。常见两类：

1. **混合检索**：向量（语义）+ 关键词（BM25），用 RRF（倒数排名融合）合并
2. **RAG Fusion**：多查询改写后各自检索，再按排名融合

**解决什么**

向量擅长语义相近，关键词擅长专有名词、型号、法条号。两路互补。

**适用场景**

- 生产默认配置之一
- 文档里专有名词多、又有口语提问

---

### 17. CRAG（Corrective RAG，纠错 RAG）

**在做什么**

给检索结果打分：

- 质量够 → 直接生成
- 质量一般 → 改写查询再检索
- 完全不够 → 回退网页搜索或其他数据源，而不是硬拿噪声生成

**解决什么**

检索失败时不要硬答。高准确率场景需要「承认搜不到」或「换一条路」。

**适用场景**

- 法律、医疗、客服里不能瞎编
- 内部库覆盖不全、需要外网兜底

## 怎么选

| 你的情况 | 更该上的组合 |
| --- | --- |
| 标准文本知识库，追求基本可用 | Simple RAG + 语义分块 |
| 尽快上线、先跑通 | Simple RAG + 语义分块 |
| 用户提问口语化、风格多变 | 查询改写 或 HyDE |
| 生产环境，追求检索质量 | Fusion（混合检索）+ Reranker |
| 准确率要求高，不能容忍幻觉 | CRAG 或 Self RAG |
| 查询有的很简单、有的很复杂 | Adaptive RAG 路由 |
| 需要跨文档多跳推理 | GraphRAG + 多级索引 |
| 成本和延迟敏感 | Self RAG + 上下文压缩 |
| 文档结构清楚（手册 / 法规） | Contextual Headers + 上下文增强 |
| 有用户行为可学 | 反馈闭环 |
| 问题很短、很残缺 | HyDE + CRAG |
| 召回结果又长又杂 | RSE + 上下文压缩 |

---

## 建议落地顺序

1. **先跑通 Simple RAG**  
   切块、向量库、TopK、生成。没有基线，后面无法判断「到底哪一环变好了」。

2. **看坏在哪一环再加模块**
   - 搜不到 → 改切块、查询改写、HyDE、Fusion
   - 搜到了但答偏 → Reranker、压缩、RSE
   - 有时简单有时复杂 → Adaptive / Self RAG
   - 要跨文档推理 → GraphRAG / 层级索引

3. **不要一上来上全家桶**  
   Multi-Agent + GraphRAG + 多模态同时上，成本高，效果也不一定更好。

4. **用评测说话**  
   常见指标（如 RAGAS）：
   - 忠实度：回答有没有瞎编
   - 答案相关性：答的是不是你问的
   - 上下文精确率：搜到的有多少是有用的
   - 上下文召回率：该搜到的搜到了吗

## 一张图记住优先级

```
切分策略 → 索引方式 → 检索与融合 → 重排与压缩 → 路由 / 纠错 → 图谱与多跳
```

前者搞不定，后者换再多模型都是徒劳。生产里最常见、性价比最高的起步组合是：

**语义分块（或递归切分）+ 混合检索 + Reranker**

有余力再按痛点加 HyDE、Self/CRAG、层级索引或 GraphRAG。

## 术语速查

| 术语 | 含义 |
| --- | --- |
| RAG | Retrieval-Augmented Generation，检索增强生成 |
| Chunk | 切出来的文档片段 |
| Embedding | 把文本变成向量 |
| TopK | 检索返回最相关的 K 条 |
| BM25 | 经典关键词检索算法 |
| RRF | Reciprocal Rank Fusion，多路排名融合 |
| Cross-Encoder | 把问题和文档拼在一起打分的精排模型 |
| HyDE | 用假想答案的向量去检索 |
| CRAG | 对检索结果纠错，差则重搜或外搜 |
| GraphRAG | 基于知识图谱的 RAG |
